# ADR-2: Rate Limiting на базе Redis в API Gateway

## Контекст (Context)
Нашему API Gateway требуется защита от DDoS-атак прикладного уровня (L7), перебора паролей (brute-force) и массового парсинга ссылок. В нашей Cloud Native архитектуре Gateway работает в виде нескольких stateless-подов (PHP-FPM) под управлением K3s. 
Локальные драйверы кэша (файлы или массивы) не подходят, так как они не шарят состояние между подами. Использование реляционной БД (PostgreSQL) также нецелесообразно: при высокочастотных инкрементах счетчиков БД будет страдать от блокировок строк (row-level locks) и разбухания таблиц (table bloat) из-за MVCC.

## Решение (Decision)
Мы приняли решение использовать **Redis** в качестве хранилища для встроенного Rate Limiter фреймворка Laravel. Фреймворк реализует алгоритм Fixed Window Counter, используя Lua-скрипты внутри Redis для обеспечения строгой атомарности операций.
В `AppServiceProvider` реализованы 4 конкретных лимитера:
- `api-public` (60 запросов / мин / IP-адрес)
- `api-auth` (300 запросов / мин / user_id)
- `link-create` (10 запросов / мин / идентификатор)
- `auth-token` (5 запросов / мин / IP-адрес)

## Последствия (Consequences)
**Положительные:**
- Быстрые атомарные инкременты через Lua-скрипты полностью исключают состояние гонки (race conditions).
- Снимается нагрузка (CPU и Disk I/O) с основной базы данных PostgreSQL — паразитный трафик отсекается на уровне кэша и роутинга (паттерн Fail Fast).
- Полная распределённость: все поды Gateway используют единые, синхронизированные счетчики.

**Отрицательные / Риски:**
- Появляется жесткая зависимость от Redis на этапе маршрутизации запросов. Если Redis упадет, API Gateway не сможет обрабатывать эндпоинты, защищенные middleware `throttle`. В production-среде потребуется обеспечение высокой доступности (High Availability) для Redis.
